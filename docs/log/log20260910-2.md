## 3. 我验证并推翻的假阳性（诚实记录）

### 3.1 ❌ RK45 DOPRI5 表系数"错误" —— 假阳性

代理 A 断言 `adaptive.rs` 第 7 行 `a[6]` 被误写成 `b5` 的 6 元素拷贝，"k[6] 被污染导致误差估计错误"。

**我的独立验证**：查阅 DOPRI5 标准表，第 7 行（FSAL 行）**本来就等于** `b5`：

```python
row6 == b5 ? True    # 这正是 DOPRI5 的 FSAL 性质，不是 bug
sum(b5*c^1) = 1/2 ✓   sum(b5*c^2) = 1/3 ✓
sum(b5*c^3) = 1/4 ✓   sum(b5*c^4) = 1/5 ✓   # 4 个阶条件全部成立
```

且 `b5[6] == 0`，故 `k[6]` 不进入 `x5`；`k[6] = f(t+dt, x5)` 的求值点 `x5` 在两种表下**完全相同**，因此 `k[6]` 相同、`x4` 相同、误差估计相同。实测：

```
correct impl x(0.5) = 1.648723958333333  embedded err = 2.050781e-05
buggy   impl x(0.5) = 1.648723958333333  embedded err = 2.050781e-05
=> 差异 1.000 倍（即毫无差异）
```

**处理**：不伪造修复。仅**补充表结构回归测试**（`test_rk45_dopri5_tableau_invariants`、`test_rk45_observed_convergence_order_is_five`，实测收敛比 > 16×），并**更正注释**（先前由我误写的"最后一项应为 35/384"是错的，已改为正确的 FSAL 说明）。

## 7. 第 3 轮：实现 `Link::delay`（传输延迟从静默忽略 → 真实建模）

第 1–2 轮披露的头号树枝链路：`Link::delay` 字段被**存储、暴露、序列化**，但传播路径**从不读取**——用户写 `with_delay(0.5)` 得到的与写 0 完全一致。对传输延迟模型（`e^{-sT}`）这意味着**相位滞后被完全移除**，能把不稳定延迟反馈回路仿真成稳定的。

### 7.1 实现（非仅报错）

选择**真实实现**而非「有延迟就报错」，因为字段已经存在且语义明确：

| 组件 | 实现 |
|------|------|
| `DelayLine` | 每链接一个**环形缓冲**，容量 `steps + 1`，内存 ∝ `delay/dt` 而**非运行时长** |
| `SignalCache::from_diagram_with_dt` | 按 `dt` 为每个延迟链接建立延迟线 |
| `SignalCache::configure_delays` | 拓扑/步长变化时重建，已缓存历史**不丢失** |
| `Scheduler::set_step_size`（新增默认方法） | 引擎每步前告知 `dt`；默认空实现保持后向兼容 |
| `propagate_signals` | 延迟链接读延迟线；未到达时发 `None`（信号未到达是「无信号」，不是 0） |
| `engine.rs` | 构造与 `reschedule` 均调用 `set_step_size` |

### 7.2 🔍 实现过程中发现并修复的真实缺陷（非一次性写对）

**① 浮点 `ceil` 导致延迟多一步**

在写延迟线时发现：

```python
3.0 * 0.1 / 0.1 = 3.0000000000000004   →   ceil = 4   （应为 3）
```

即**请求恰好 3 步延迟，实际得到 4 步**。已修正为「先在相对 epsilon 内吸附到最近整数，再取 ceil」。回归测试覆盖 7 组「看似精确但二进制不精确」的倍数（`0.1×3/5/7`、`0.01×5`、`0.2×3`、`0.05×6`、`0.3×2`）。

**逆向验证**（还原无容差版本）：

```
assertion `left == right` failed: dt=0.1, delay=3*dt: the lag must be exactly 3 steps
  left: Some(None)      ← 信号尚未到达，延迟实际为 4 步
  right: Some(Scalar(0.0))
```

**② 我自己在环形缓冲容量上的推理错误（诚实记录）**

我一度把容量改为 `steps` 并「推理证明」正确（用 Python 模拟似乎自洽），结果 3 步延迟变成 4 步。正确的容量是 `steps + 1`：因为**先 push 再 read**，缓冲恰好为 `steps` 时读到的是 `steps - 1` 步前的值。已改回并加注释说明为何多一个槽位。

### 7.3 本轮的延迟语义（已钉死）

`delay = N · dt` ⇒ 目的端在**第 N 步**收到源端**第 0 步**的值；前 N 步为 `None`。

实测输出（`delay = 3·dt`）：

```
[None, None, None, 0.0, 1.0, 2.0, 3.0]   ← 恰好滞后 3 步
```

## 9. 第 5 轮：事件路由结构化 + 耦合收敛报错

### 9.1 事件路由：字符串拼接 → 结构化字段

原实现：入队时 `format!("zc:{block_id}:{idx}:{seq}")`，出队时 `event.id.split(':').nth(1)` 还原目标。`BlockId` 含 `:`（如 `"plant:gain"`）时**被截断为 `"plant"`** → `dispatch_event` 报 `block not found`，把合法模型变成硬错误。

**修复**：`Event` 新增结构化字段 `target: Option<String>` 与构造器 `with_target()`；路由直接读字段，不再解析字符串。无 target 的事件视为自由事件，**不投递给任何块**（而非投给空名块）。

**逆向验证**（还原字符串解析）：

```

test_event_routing_handles_a_block_id_containing_a_colon ... FAILED
```

恢复后通过。同时更新了 4 个依赖旧编码的测试，并新增 `test_event_without_a_target_is_not_dispatched_to_a_block`。

### 9.2 耦合收敛：死字段 + 静默不收敛

| `ConvergenceCriteria::relative_tolerance` **从未被读取**（死在结构体里） | 新增 `check_convergence_scaled(delta, scale)`，实现 `\|Δ\| <= atol + rtol·\|scale\|` |

## 10. 第 6 轮：独立验证推翻了我第 5 轮的部分修复

第 5 轮结束后我再次发起**对抗式独立验证**（要求“尝试推翻每一条声明”）。它找到了我**自己引入的三个真实缺陷**，以及两处早已存在的“空测试”。本轮全部修复。

### 10.1 我引入的缺陷（诚实披露）

**① `converged` 让常量漂移被误判为收敛（高）**

我用 `scale = max\|new\|` 配合 `atol + rtol·\|scale\|`。在大量级下这个判据会接受**任意绝对漂移**：

```
jacobi_coupling(u = x + 500) 于字段 1e9：
  rtol*scale = 1e-6 * 1e9 = 1000 > 500   -> 第 1 次迭代就“收敛”
  但把映射再应用一次，值仍然改变 500 —— 它根本不是不动点
```

**② `Max` 吞掉 NaN（高）** —— `0.0_f64.max(NaN) == 0.0`，所以用 `max_delta.max(delta.abs())` 累加残差会把 NaN 变成 `0.0`，而 `0.0` 总能通过收敛测试：

```
fixed_point_iteration(&[field(0.0)], 映射 -> NaN)  ->  Ok([NaN])   ← 以成功报出损坏的迭代值
```

新增 `finite_max_propagating` 辅助函数（非有限值**具粘性**），三个迭代函数全部改用。**逆向验证**（还原普通 `max`）：

```
test_nan_residual_is_not_reported_as_converged ... FAILED
  a NaN iterate must not be reported as converged, got Ok(Ok([NaN]))
```

**③ 零交叉检测的语义缺陷（高/中）** —— 我写的 `sign_change || val == 0.0` 有两个问题：

| 问题 | 后果 | 修复 |
|------|------|------|
| `val == 0.0` 与符号变化无关 | `-1, 0, -1`（未穿越）被报为穿越 | 仅当**伴有符号变化**时才算穿越 |
| 长时间停在 0 | **每步**都触发（10 s 运行产生 10000 个事件） | 首次观测后的零不再触发 |
| NaN 后未清历史 | `-1 → NaN → +1` 报出“穿过 NaN”的跨界穿越 | 非有限值**清除**该索引历史 |
| 索引复用 | 交叉信号数量变化时，同一索引对应**不同**物理量 | 每步 `retain` 剪除消失的信号历史 |

新增 4 项测试（`test_zero_touch_without_sign_change_is_not_a_crossing`、`test_signal_stuck_at_zero_does_not_refire`、`test_non_finite_sample_resets_history_across_the_gap`、`test_stale_crossing_history_is_pruned`）。

**④ 日志上限在校验后才生效** —— 单步报出 N 个穿越时会瞬时持有 `4096 + N` 条。改为**循环内**限定。

**⑤ 延迟线的急切分配（中）** —— `VecDeque::with_capacity(steps + 1)` 会为每个延迟链接**预先**保留 46 MiB（`steps = 1e6` 时），而 `delay=1 s, dt=1e-6` 是合法配置。改为**惰性增长**，并把上限提取为具名常量 `MAX_DELAY_STEPS`。

### 10.2 我又一次“推理错误”（诚实记录）

我曾试图用一个额外的「相对步长」条件（`|Δ|/\|x\| <= rtol`）去堵住常量漂移。实测立刻推到：对**完全收敛**的映射 `x ← 0.5x`，`|Δ|/\|x\|` **恒为 1.0**，因为 `x` 与 `Δ` 同步缩小——这个条件会拒绝一切收敛到零的迭代。已**撤回**该条件，并在 `converged` 的文档里如实写明局限：单步判据无法区分“已settle”与“匀速漂移”，因此调用方的正确做法是**预算耗尽即报错**，而不是把漂移当作成功。

### 10.3 验证发现的两处“空测试”（早已存在）

| 位置 | 问题 | 修复 |
|------|------|------|
| `domains/analog/mna.rs` `test_mna_singular_detection` | `if let Ok(sol) = result { … }`：奇异系统返回 `Err`，所以**断言体从不执行**，删掉 `solve()` 也能通过 | 改为穷尽匹配：`Err` 必须报“singular”，`Ok` 必须为有限值且满足平凡解 |

### 13.2 第 5 项的失败尝试（诚实记录，这是本轮最重要的部分）

我最初把第 5 项理解为「**扩展宏以支持非标量字段**」，并投入了大量改动（约 500 行宏 + 4 个块改调用点）。**该方案失败了**，失败原因是结构性的，不是努力不够。

在隔离环境（`/tmp/scico_probe/`）中逐条验证出 `macro_rules!` 的六条硬约束：

| # | 约束 | 实测现象 |
|---|------|----------|
| 1 | 裸 `{}` 不能作为 `tt` 重复的**首 token** | rustc 报**伪** `recursion limit reached`，而非干净的 mismatch |
| 2 | `expr` 片段后**不能**紧跟 `[` | `$v:expr, [$s:tt]` → `not allowed after expr fragments` |
| 3 | `tt` 是**不可分**单位 | 无法容纳 `pad_to(4)`；`$(, $t:tt)*` 后接 `,` 是**局部歧义** |
| 4 | `$($rest)*` 转发会**折叠为单个不透明 `tt`** | 多条目递归在第 2 项后即断裂（`SPLIT-NOMATCH [k => T,]`） |
| 5 | 单步臂**前缀匹配获胜** | 多步变换链永远走不到递归臂 |
| 6 | 不能用 `tt` 累加器**构造表达式** | `@acc` 方案被 rustc 拒绝 |

第 1–3 条**互相冲突**：匹配带参步骤需要 `tt`，传递值需要 `expr`，而二者不能相邻。这是 `macro_rules!` 的表达力边界——只有 proc-macro 能解决，那是一个独立 crate（引入 syn/quote、重开一条已稳定的序列化契约）。

**判断失误**：我在 §11 中曾把第 5 项定性为「手写是**有注册表级测试兵守**的」，即**当时已判定它不是缺陷**。后来却把它重新定义为「架构级不统一」并用最大方案去解。这是教科书式的过度工程——为一个**假设性的未来收益**（「以后新增此类块更方便」）付出了真实成本，并把工作卡死。

### 13.3 最终方案：删除宏，回归传统手写 + 修复真实缺陷

**宏已完全删除**：`src/scico_config.rs` 移除，`lib.rs` 的 `#[macro_use] mod scico_config;` 移除，全仓 `grep -rn scico_config src/` **零匹配**。

14 处调用点全部展开为手写 `configuration` / `apply_configuration`，行为与宏生成版**逐字段等价**（含按名排序的 `configuration()` 输出顺序）。

**同时修掉一个真实缺陷**：借展开之机，为 4 个非标量块补上了**元素级有限性校验**。此前手写实现直接 `clone()`，手改 JSON 可向系数/状态向量注入 `NaN`，污染此后**每一次**求值：

| 块 | 修复 |
|---|---|
| `TransferFunction` | `num`/`den` 逐元素有限性校验；`den` 额外要求非空 |
| `StateSpaceSystem` | `a` 校验形状 + 数据长度 + 有限性；`b`/`c`/`d` 各自校验 |
| `MatrixMultiply` | 非有限数据**整体拒绝**，不写入 |
| `DiscreteFilter` | 系数逐元素校验；`a[0] == 0` 提前拒绝（否则 `IIRFilter::new` 会 panic） |

新增共享辅助 `core::param::all_finite`，使校验逻辑**只有一份**。

### 13.5 本轮教训

1. **先算账，再动手**。同一个目标常有更小的方案：第 5 项的真正缺陷是**缺 NaN 校验**（4 个 `if` 守卫即可），而不是「宏不支持非标量」。我却选了改动面最大的路径。
2. **「看起来更整齐」不是需求**。把 24 个手写实现收编进宏，收益是审美，成本是表达式边界风险。
3. **撞到第 3 次约束就该停**。我说过「撞上第三种限制就回退」，实际撞到第六种才停——判断失误在我。
4. **失败也要如实入账**。本节完整保留了六个失败探针的结论，下一个尝试者不必重新推导。
