#### 4.2.1 依赖与特性门控

`Cargo.toml` 新增（全部 optional，默认构建零新增依赖）：

```toml
wgpu = { version = "30.0.1", optional = true, default-features = false,
         features = ["std", "parking_lot", "metal", "vulkan", "dx12", "gles", "wgsl"] }
pollster = { version = "1.0.1", optional = true }

[features]
gpu = ["wgpu", "pollster"]
```

#### 4.2.2 新增模块（遵循原则 1：模块化）

```
src/core/compute/gpu/
  mod.rs            — WgpuBackend 实现 GpuBackend + install_global_gpu_backend()
  device.rs         — 适配器/设备获取、能力探测、GpuPrecision
  kernels.rs        — 管线编译与带类型的启动封装
  pool.rs           — 持久化 GPU 缓冲区池（按角色 + 2 的幂分桶）
  precision32.wgsl  — f32 存储内核（全平台可用）
  precision64.wgsl  — f64 存储内核（需 SHADER_F64）
```

#### 4.2.3 ⚠️ 关键技术发现：f64 并非全平台可用

原始设计按文档注释拟采用 `array<f64>`。**实测证明该假设错误**：

```
adapters: 1
  Metal Apple M4 f64=false        ← SHADER_F64 = false
```

`wgpu::Features::SHADER_F64` 在 Apple Silicon Metal 上缺失。若强行声明 `f64` 存储缓冲区，`create_shader_module` 直接失败。

**解决方案**：设备创建时探测一次，选择匹配的内核集：

| 适配器能力 | 内核集 | `GpuPrecision` |
|-----------|--------|----------------|
| 支持 `SHADER_F64` | `precision64.wgsl` | `F64` |
| 不支持 | `precision32.wgsl` | `F32` |

并新增 `GpuBackend::supports_f64()`（默认 `true`）：返回 `false` 时，自适应调度器**将 f64 工作负载保留在 CPU**，而非静默降精度（规避 trap.md 第 1 条"浮点精度不统一"）。这一防降级行为有专门测试 `gpu_backend_drives_adaptive_dispatcher` 覆盖。

#### 4.2.4 WGSL 内核实现

| 内核 | 入口 | 说明 |
|------|------|------|
| 分块 GEMM | `matmul_main` | **16×16 workgroup 共享内存分块**，全局访存降低 16× |
| 逐元素 | `binary_main` | add / sub / mul（Hadamard），op 标签选择 |
| 标量乘 | `scale_main` | `out = s·a` |
| AXPY | `axpy_main` | `out = α·x + y` |
| 归约 stage1 | `reduce_partial` | 每 workgroup 产出 1 个部分和，256 线程树形归约 |
| 归约 stage2 | `reduce_finalize` | 折叠部分和到 `out[0]` |

#### 4.2.5 开发中定位并修复的真实缺陷（全部经实测确认）

| # | 缺陷 | 定位方式 | 修复 |
|---|------|---------|------|
| 1 | `u64(scale_dims.z) << 32u` 触发 naga `Unable to cast` | naga 解析验证 | f32 内核改用单 u32 槽位 bit-cast；f64 内核用 `u64(lo) \| (u64(hi)<<32)` |
| 2 | `vec4<u32>` uniform 读取 `.y` 取到 0（nv12 16 字节 stride 规约） | 实测 `scale=0` 导致返回值全 0 | scale/axpy 的控制载荷改为 `array<u32>` storage 绑定，4×u32 = 16 字节恰好满足对齐 |
| 3 | `axpy_y` 声明为 `read` 却写入 → `InvalidStorePointer` | 用 naga 对 `precision64.wgsl` 校验捕获 | AXPY 改为 `(x, y, out)` 三输入 + 独立输出绑定 |
| 4 | 绑定组与着色器声明不匹配 → 管线创建失败 | wgpu 校验错误 | 按各着色器实际声明一一对齐 layout |
| 5 | `download()` 按 f64 宽度(8B)切片，但缓冲池按 f32(4B)分配 → 越界 | `slice offset 0 size 8584 is out of range for buffer of size 8192` | 改为按 `precision.element_size()` 计算字节长度 |

第 5 项特别值得记录：这是**在参数化精度之后才暴露的越界缺陷**，属于 trap.md 第 12 条"数学运算边界缺失检查"的实际案例。

#### 4.2.6 缓冲区池（性能优化）

初次实现每次调用创建 3–4 个缓冲区。新增 `pool.rs`：

- 按 `BufferRole`（Input / Output / Readback / Control）分桶；
- 容量向上取整到 2 的幂 → 长期运行最多 `log2` 个桶，膨胀 < 2×；
- `PooledBuffer` 的 `Drop` 自动归还 → `?` 提前返回也不会泄漏。

### 4.3 GPU 性能实测（诚实结论）

`examples/gpu_bench.rs`（同时验证正确性与性能）：

```
device        : wgpu/Metal/Apple M4
precision     : F32
f64 kernels   : no (f32 kernels; f64 workloads stay on the CPU by default)
max elements  : 33554431

size   64³:  cpu-rayon  18.55 GFLOPS | gpu  0.89 GFLOPS   0.05×
size  256³:  cpu-rayon  61.50 GFLOPS | gpu 15.11 GFLOPS   0.25×
size  512³:  cpu-rayon 101.91 GFLOPS | gpu 47.40 GFLOPS   0.47×
size  768³:  cpu-rayon 106.83 GFLOPS | gpu 60.32 GFLOPS   0.56×
size 1024³:  cpu-rayon 115.81 GFLOPS | gpu 84.70 GFLOPS   0.73×
所有尺寸: max |Δ| gpu vs cpu ≤ 7.07e-05（f32 精度内）
```

**结论：GPU 在集显上不占优，且差距源于固定开销而非算力。** 通过专项实验定位（全部实测）：

- 空 encoder 提交 + 阻塞轮询：**0.026 ms**
- 提交 + `map_async` + 轮询 + 读取：**0.080 ms**
- 实际 `mat_mul` 单次耗时：**0.62 ms**（4×4 与 1024³ 的小尺寸下几乎相同）

即 ~0.55 ms 是不可分摊的**每次调用同步往返延迟**。`16×16` 共享内存分块已将 GPU 从 38.9 → 84.7 GFLOPS（1024³ 下 2.2×），但同步 API 无法隐藏该延迟。

**处理方式（拒绝虚假宣称）**：不宣称"GPU 更快"，而是把实测结论编码为策略：

- `ComputeConfig::integrated_gpu()` — 集显保守阈值（`gpu_threshold = 16e6`），因集显共享内存且延迟大。
- `ComputeConfig::discrete_gpu()` — 独显激进阈值（`gpu_threshold = 1e6`），因独显有专用显存、带宽高得多，交叉点远早于此。
- 阈值表以实测数据写入 `ComputeConfig` 的文档注释。

if total_time.is_finite() && total_time >= 0.0 {
    if stride.is_finite() && stride > 0.0 {

### 6.2 `drive_efficiency` 静默错误（缺陷 4）

修复前：

```rust
let _total_loss = motor_loss + converter_loss;   // 算了就丢
output_power / total_in                          // 两个损耗参数完全无效
```

修复后语义明确：

```text
η = (input_power − motor_loss − converter_loss) / input_power
```

并支持回退：未提供损耗时用 `input_power − output_power` 推断，避免两者同时生效造成重复计入；结果 clamp 到 `[0,1]`；非有限/非正输入返回 `0.0`。

**特别注意**：原有测试 `test_drive_efficiency` 断言 `0.9`——正是**与被测缺陷绑定的错误期望**（0.9 就是 `900/1000`，即忽略损耗的结果）。按 principle 第 19/20 条，不得直接 `#[ignore]`，必须修正测试与被测代码。已改写为 5 个物理正确性测试，其中 `test_drive_efficiency_losses_reduce_efficiency` 专门断言"损耗越大效率越低"，正是原缺陷无法通过的断言。

### 6.5 VOF `step()` 补全真实实现（缺陷 7）

按 principle 第 15 条"功能修复必须完整闭环"，不是改注释，而是**实现缺失的投影步**：

新增 `VofSolver2D::projection_step()`：

1. 中心差分求速度散度 `∇·u`；
2. Jacobi 迭代求解 `∇²p = ρ·∇·u/Δt`（50 次固定迭代，保证确定性）；
3. `u -= Δt·(∇p)/ρ`（按局部变密度缩放，`ρ` 来自已推进的体积分数）。

新增 `max_abs_divergence()` 作为可观测量。

**验证过程中的一个诚实纠错**：我最初的测试用**线性速度场**（`u = 0.5i`）验证散度下降，结果失败（50 → 73.7）。经独立数值实验确认：线性场的散度是常量，小尺寸 Dirichlet 盒上无论 Poisson 解多收敛，修正都受边界限制而无法归零——**是测试用场不合数学前提，不是实现错误**。改用良态场重新验证：

- 解析无散度场 `(sin πx·cos πy, −cos πx·sin πy)`：投影前后 `max|div|` 均 < 1e-9 → **不引入散度**（专门捕获压力梯度符号错误）；
- 局部源场：`max|div|` 由 `5.0e1` 降至 `1.9e1`（2.6× 下降）→ **确实在做投影**。

新增 4 个测试：`test_step_performs_projection_not_only_advection`、`test_projection_preserves_a_divergence_free_field`、`test_step_rejects_invalid_grid_and_timestep`、`test_phi_stays_bounded_after_steps`。

## 8. 未完成项 / 后续建议（诚实披露）

以下为扫描发现但**本轮未修复**的问题，不隐藏：

1. **`test_tracer_new` / `test_zvs_condition` 仍是弱测试** — 需要为 `NonSequentialRayTracer` 与 `DabConverter::zvs_condition` 补齐真实物理断言，属独立小任务。
2. **`nonlinear_fea.rs` 单元刚度装配** — 每个单元的局部刚度都累加到同一左上角块，对多单元网格结果不正确。根因是 `TrussElement`/`BeamElement` 不含节点连接信息；修复需要扩展单元数据结构，属跨模块改动，风险较高，建议单独排期。
3. **`postproc/batch.rs` 与 `hilsupport.rs` 的占位行为** — `ParameterSweep::run` / `BatchSimManager::run_all` 仅写元数据桩、`HilRunner::step` 丢弃 `dt` 与引擎结果。这些需要接入真实引擎，属较大范围集成任务。
4. **GPU 同步往返延迟** — 当前 GPU 后端是同步 API（符合 `GpuBackend` trait 契约）。要真正发挥 GPU 性能需批量提交/异步管线，属架构级改动。
5. **集显上 GPU 不占优** — 已通过阈值策略诚实处理（§4.3），而非宣称虚假加速。独显用户可通过 `ComputeConfig::discrete_gpu()` 启用。

## 9. 结论

- 本项目在**结构层面**确实已达到"强骨架 + 强落地"，而非空壳：`todo!`/空实现/dead code/`block_on` 违规均为 0。
- 但**并非"零问题"**：本轮定位并修复了 2 个可挂死死循环、1 个 usize 下溢、1 个静默错误结果、2 处错误吞没、1 处文档欺骗、1 处缺失的物理步骤，以及基线 Clippy 的 2 个真实错误。
- **wgpu 30.0.1 GPU 加速已从"接口幻觉"变为真实能力**：6 个 WGSL 内核、完整 Rust 后端、真机 26 项正确性验证。过程中发现并解决了"f64 存储全平台可用"这一错误假设（Apple M4 实测不支持 `SHADER_F64`），并以"精度感知调度 + 拒绝静默降精度"处理。

- 所有修复均遵循 principle 第 14–18 条：可观测行为变化 + 回归测试 + clippy 零警告 + 真实 diff 链路。
