5. 是否存在“文档写得很完整，但代码实现和架构很松散”的欺骗式状态

- 但还存在 3 类值得继续改进的核心问题：

## 5. 代码层面的发现：已完成项的修正与改进建议

### 5.1 已完成但仍需改善的部分

#### A. 计算平台有统一意图，但还存在重复功能层
已在 `src/core/compute/` 中看到成熟的统一计算平台：
- `backend.rs`
- `matrix.rs`
- `linalg.rs`
- `vector.rs`
- `fft.rs`
- `integration.rs`
- `simd.rs`
- `vendor_blas.rs`
- `vendor_ffi.rs`

这说明项目已经意识到“统一计算核心”的重要性，且实现相当完整。

但从实际工程角度看，仍存在“重复功能/不同层面各自实现”的问题：
- 多个领域模块直接实现自己的数值小循环，带来代码重复
- 线性代数/向量操作在不同子系统中可能有相似但不一致的实现路径
- 一些高度并行化的能力已具备，但没有完全统一成全局标准调用规范

结论：
- 统一计算平台已形成骨架，整体方向正确；
- 下一阶段重点是“全项目收敛”，而不是再增开新的计算接口。

#### B. 并行化已存在，但尚未全部达成统一策略
已经看到在项目中大量使用了 Rayon、并行遍历和工作流调度：
- `runtime/workflow/parallel.rs`
- `src/core/compute/backend.rs`
- `src/core/compute/matrix.rs`
- `src/domains/structural/fem_solver.rs`
- `src/domains/fluid/navier_stokes.rs`
- `src/domains/thermal/conduction_3d.rs`
- `src/domains/astrophysics/orbital.rs`
- `src/coupling/field_mapping.rs`

这说明并行化不是空谈，而是项目真实能力之一。

但是并行化策略仍需要进一步统一：
- 工作量阈值策略应该在统一门面中集中管理，而不是散落在各领域模块中
- 每个领域模块都要明确使用 `core::compute::backend::global()` 作为唯一入口
- 不要出现“某模块自己又写一套 parallel loop / 不一致 threshold / 自定义 tile”。

#### C. 文档蓝图完成度高，但需要继续纠偏“实现真实性”
蓝图是很丰富的，尤其 `BLUE10` 和 `BLUE11` 的设计很完善，说明路线图和阶段拆解已经非常成熟。

但仍需提醒：
- 蓝图是“架构设计”，不等于“代码已全部落地成立”
- 真实工程必须要求“文档和代码同步”，否则会形成伪完整状态
- 在长期维护中，真正的紧要任务是：
  - 把发现的重复计算统一
  - 把 warm path 的 hot loop 收敛到统一平台
  - 把多领域并行调用当作标准而非例外

## 6. 全项目扫描中的“重复计算”问题清单

### 6.1 典型重复功能

下面这些是最典型的重复功能/重复模式，值得统一：

1. 向量/矩阵乘法与线性代数操作
   - 各领域重复实现的矩阵乘法、LU/SVD/求解器路径
   - 统一目标：所有真实计算都通过 `src/core/compute` 入口

2. 标量/向量归一化与范数计算
   - `norm`, `distance`, `dot`, `sum` 等在模块间可能重复但“形态不一致”
   - 统一目标：所有逻辑必须调用 `core::compute::vector` 和 `core::compute::linalg`

3. 热/流/结构/电磁的迭代求解
   - 部分模块各自写 Jacobi/Gauss-Seidel/并行 sweep 循环
   - 统一目标：抽离统一求解器层与收敛策略层

4. 事件处理与边沿检测
   - 零交叉/事件检测在不同模块中可能分别实现
   - 统一目标：shared `runtime/event`/`runtime/algebraic` 方案作为全局门面

5. 分析与后处理统计量
   - 均值、RMS、FFT、功率谱等在多个模块中重复
   - 统一目标：后处理层应集中到 `postproc`/`recorder` 等公共接口

### 6.2 统一建议：计算平台收敛方案

建议采用“单一计算入口 + 多实现但同一命名结构”的方法：

1. 保留 `src/core/compute/` 作为唯一正统入口
   - `backend`, `matrix`, `vector`, `linalg`, `fft`, `integration`
2. 所有领域模块只能调用这些 API，不再自己实现重复的低层循环
3. 对每个高频操作做统一阈值策略：
   - small workload → serial
   - medium workload → parallel CPU
   - large workload → vendor BLAS / GPU if available
4. 所有 key functions 做做一个项目级规范：
   - `mat_mul` via `backend::global()`
   - `dot` via unified `vector::dot`
   - `norm` via `linalg::nrm2`
   - `solve_linear` via canonical matrix solve
5. 把所有平台特异能力控制在较小范围：
   - CPU: Rayon
   - vendor BLAS: MKL / OpenBLAS / cuBLAS
   - GPU: runtime adapter
   - 统一 fallback path

### 6.3 并行化建议

1. 先统一并行粒度阈值
   - 例如：
     - 低于 1k 元素：串行
     - 1k ~ 64k：Rayon
     - 64k ~ 1M：vendor/cpu
     - > 1M：GPU/并行分块
2. 统一“分块 + 汇总”的实现范式
   - 所有大规模矩阵、场量、迭代更新都使用 chunk/split/reduce 模式
3. 严格避免“线程池创建过多 / 每次小规模独立创建线程”
4. 所有并行算法必须满足：
   - 纯函数
   - 分块独立
   - 无共享写冲突
   - 结果归并可验证
